# ASTOP customer journey

Source: ASTOP Customer Journey v 1.0, reconciled against License Order v2.6 and Software Protection Policy v1.5. Curated October edition; not an executed agreement or proof that checkout is deployed.

## Discover and assess fit
Public visitors may learn about ASTOP and ask questions without supplying identity documents. Determine whether repeated observation, supervision or monitoring causes material model calls, token traffic or delayed decisions. Identify the task, host, intended accelerator, relevant events and acceptable decision delay. For a one-shot task, cheap checks or already sufficient webhooks, ASTOP may provide little incremental value. Choosing not to use it is a valid outcome.

## Choose the appropriate access route
Individuals may request one named seat; organizations may request two or more named seats. Enterprise evaluations remain separately scoped and protected. Retail access does not universally require an NDA or enterprise evaluation. The journey's USD 19 and twelve-download illustration is superseded by LO v2.6: USD 20 for an individual, USD 16 per organization seat with at least two seats, eligible 10% Branch discount without stacking. Seat rights are not a fixed number of unrestricted downloads.

Verify the legal counterparty and email, present the exact order and governing terms, record acceptance, confirm payment through a trusted provider, then issue the appropriate license and signed build. Account creation, successful payment redirects and a Branch code alone do not grant delivery rights. If online commerce is unavailable, explain that status and arrange the next step with itriX.

## Install, activate and configure
Use the supported build for the operating system and CPU architecture. Linux x 86_64 and Linux ARM 64 are distinct; ARM 64 does not mean AMD x 86. Windows access through WSL is not a native Windows GUI claim. Verify installation, permissions, relevant telemetry and the active entitlement. Missing sensors are unavailable values, not measured zeros. Determine which events should wake the agent and which required terminal/failure events must be preserved. Do not blindly invoke every telemetry command or assume adding a global instruction guarantees useful ASTOP behavior.

## Compare and decide
Define and version the baseline before comparing conventional polling with event-driven observation. Keep workload, model, environment, useful decisions and acceptance criteria comparable. Record calls, observation-induced tokens, delivered bytes, missed/incorrect decisions, event latency and observer resource cost. Material baseline errors may be corrected with the reason recorded and affected comparisons rerun. A successful example is not evidence of a 24-hour test or universal savings.

Choose continue, tune, stop, request refund review or separately scope an expansion. Refund requests normally have a 30-calendar-day window; approval and rights revocation follow the LO. Expansion is a separate decision. ASTOP use is not a mandatory prerequisite for AXIOM Compute, AXIOM Core or QNTA Runtime.
